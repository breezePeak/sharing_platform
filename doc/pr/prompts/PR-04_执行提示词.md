## 一、接入路由与产品输入

旧 XML 按认证 callerId/type 唯一匹配启用路由；新入口使用授权 endpointId 和源/目标根目录引用。为路由补最小配置：调用方、type、sourceRoot、endpoint、targetRoot、通知配置及版本。

一个 product 对应一个产品目录，单独 ZIP/TIFF 也须放入目录；productName 只作显示，不拼路径。fileCount 校验产品数量，物理文件数单独统计。保存原始产品全集，并冻结本任务使用的配置和凭据版本引用。

目标按既有约定隔离为 `targetRoot/sourceCode/taskId/productId/relativePath`，任务级 `_manifest.xml` 与 `_READY` 放任务根目录。用于目录的标识经过安全校验或稳定无碰撞编码，不能直接拼未经校验的调用方输入。

## 二、实现预检查和固定清单

按以下顺序落实检查；每项记录结果与可定位原因，失败可以提前结束，不能用 exists 或登录成功代替整套检查。

1. 参数和数量：必填项、时间格式、产品 ID 约束及唯一性、fileCount 与产品节点数一致。
2. 路由和权限：唯一启用路由、连接与源/目标范围有权限，形成任务快照。
3. 路径和对象：检查本地真实路径及每级目录，拒绝越界、符号链接、特殊文件、重复或相互包含的产品范围。
4. 文件集合：递归列举普通文件并保留目录结构；产品不能为空；按明确配置处理临时名、控制文件和零字节文件；检查目标重名、大小写及临时命名冲突。
5. 源内容：逐文件流式完整读取，统计 long 字节数与 SHA-256，记录读取前后属性；读完再次核对目录集合。发生变化或不可读时拒绝。
6. 固定清单：持久化产品全集、目录、相对路径、大小、预期摘要、清单版本和摘要。冻结后不可因源变化重算一份基准继续放行。
7. 目标条件：实际检测本次所需连接、写入、严格校验、改名及目标隔离条件；区分原任务残留、已发布内容和其他冲突。已知空间不足拒绝，容量无法获取记未知。

没有生产方应交付清单时，只保证观察到的固定集合，不把扫描结果当作能证明上游没有漏生成文件。

预检通过或拒绝结果与反馈通知同事务保存。通过后进入 WAITING_FEEDBACK，取得约定 ACK 才能上传业务文件；探测文件不算业务交付。预检拒绝发送 doAsk result=1/rejectrason 或新协议等价反馈，默认不再生成 doComplete。

## 三、逐文件上传并核验实际内容

领取任务后使用原快照和固定清单，在本任务独占临时区域传输。临时文件不能与合法业务文件重名，所有流和连接正常或异常都释放。

每个文件分别保存预检基准、上传实际读取值、目标实际验证值，并满足：

    清单大小 = 上传实际读取字节数 = 目标实际字节数
    清单 SHA-256 = 上传读取摘要 = 目标实际内容摘要

FTP 检查最终命令响应，SFTP 按自身读写关闭结果判断。目标支持可信远端 SHA-256 时实际查询；不支持时完整回读目标业务文件计算摘要。只比 SIZE、只上传/回读 `.sha256` 文本都不算完成严格校验。两条验证路径都不可用时拒绝严格推送，不降级成功。

文件验证通过后再发布其正式名，并确认改名结果。暂时网络错误按配置有限重试，默认首次之外最多 3 次，首版未完成文件从头传；已验证文件只有重新核对固定基准后才能复用。源摘要或集合变化时结束原基准任务，不能混用新内容。

## 四、最后发布整单，并处理响应丢失

全部产品和文件完成后复查：源集合未变化、目标文件/目录与清单一致、每个文件验证通过、没有不属于本单的业务文件或未处理临时冲突。任何一项不满足，不发布 `_READY`。

固定 `_manifest.xml` 的字节与摘要，上传并验证实际清单。再生成绑定 taskId、清单摘要和产品数的 `_READY`，临时写入后最后发布并回读核对。接收方必须按已约定标记消费；不能称 FTP/SFTP 支持跨文件事务。

外部发布前持久化发布意图、任务标识、清单摘要和目标位置。标记写入或改名响应丢失时进入 RECONCILING，读实际标记/清单核对；未核清前不发失败完成单、不覆盖旧成果，也不先失败后成功。

该核对路径在本 PR 就要可运行，不能把发布不确定性全部推到 PR-08 才处理。

## 五、落库结果、完成通知与真实进度

确认有效发布后，保存成功结果和固定完成通知；旧 XML status=0。确认执行失败且没有有效发布时按 status=1，失败和未执行产品仍保留在原产品全集中；status=2 不用作进行中或普通取消。

通知失败只补发原通知，不重传文件，不把已验证的执行成功回退成传输失败。完成单目标路径按协议返回相对交付位置，失败路径仅供诊断。

区分上传、目标验证、发布、通知四个阶段。回读校验流量和重传流量不重复计入已完成业务字节；上传 100% 不等于整单成功。

## 六、真实链路验证与交付边界

用隔离 FTP/SFTP、PostgreSQL 和本地业务接收端分别验证整条链路。除正常多产品、多层目录外，必须实际制造同大小内容损坏、源修改、预检 ACK 丢失、READY 生效但响应丢失、完成通知 ACK 丢失，并观察是否有违规发布或重复上传。

输出原/新协议示例、清单和标记示例、运行命令及真实结果。旧 XML 暂定样例通过与客户联调通过分开报告。不增加暂停取消、自动删除、分片续传或其他协议。回退仅关闭新 PUSH 受理，保留成果、通知与待核对记录。
