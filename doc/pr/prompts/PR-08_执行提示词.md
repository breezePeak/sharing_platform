## 一、建立隔离且可重复运行的测试环境

复用已有测试夹具，准备真实 FTP、SFTP、PostgreSQL 和本地 HTTP 业务接收端。记录 JDK、数据库、驱动、迁移工具和协议服务版本；目标部署版本已确定时保持主版本一致，未确定则明确兼容验证边界。

测试数据库与数据目录必须和开发/生产隔离，不连接资料里的客户地址。接收端支持正常 ACK、持久化后丢 ACK、提前回执、延迟、重复和冲突回执。

故障通过测试钩子、受控代理或进程终止精确注入。对每个场景记录触发点、进程/连接状态、恢复动作、数据库记录、文件摘要、标记和实际传输次数，不只检查最终 HTTP 状态。

## 二、逐个验证并修复恢复窗口

以下位置分别中断并重新启动，使用原任务、配置快照、固定清单和交付身份恢复：

| 中断位置 | 恢复后必须满足 |
|---|---|
| 新任务已提交 | 找回同一任务，不丢失或生成第二次有效执行 |
| 预检结果已保存、反馈未 ACK | 恢复原通知，取得 ACK 前不上传业务数据 |
| 上传/下载半途 | 先核对固定基准，再重传本任务未完成文件；源变化不混传 |
| 文件已传、校验记录未提交 | 核验实际文件，不凭文件存在或大小相同认定成功 |
| READY 已生效、成功事务未提交 | 对照原清单/标记核实并恢复成功，只补唯一完成通知 |
| READY 是否生效仍未知 | 保持 RECONCILING，有界核对和待处理提示，不发相反终态 |
| 拉取已发布、通知事务未完成 | 根据发布意图和实际文件恢复原 transferId、位置及唯一通知 |
| 通知已被接收、ACK 丢失 | 同编号、同报文重发，不发生业务文件再次传输 |
| 等待业务验收 | 保留原数据位置和 transferId，继续等待，不重新下载 |
| 回执已提交、回复丢失 | 重复回执返回原结果，不回退状态 |
| 监听扫描中或错过周期 | 保留基线/候选/去重历史，核对后合并补扫 |

恢复执行也要原子领取并遵守并发额度，旧执行尝试的迟到写回必须失效。不能把所有 RUNNING 一律改 QUEUED；不能为恢复成功绕过源版本、路径、SFTP 主机身份或目标冲突检查。

发现恢复缺陷，修复对应现有组件并新增回归测试，不另外建立一套只供验收使用的恢复流程。

## 三、回归幂等、完整性、资源和安全

在两种协议上分别验证同大小篡改、断网、空间不足/写入失败、无数据进展超时和发布响应丢失。

在 PostgreSQL 上并发提交同 taskId、同时触发重叠监听/API、重复补发通知和回执，核对任务数、有效领取数、交付数、通知唯一性与实际上传/下载次数。

模拟扫描池/传输池/通知池满、一个目标持续超时及目录部分失败，确认队列有界、任务不丢、独立目标还能继续。验证启停/配置编辑/重启后历史快照、来源身份与去重记录保留。

回归管理权限、API 访问范围、CSRF、XML 外部实体/体积限制、路径越界和链接、XSS、日志脱敏、SFTP 主机身份。与原功能无关的重构和新增需求留出本 PR，不扩范围。

沿用原任务书的测试初值：至少 1,000 个小文件和一个不小于 256 MiB 的二进制文件。它们是测试配置，不是用户规定的业务规模。环境不足可调整，但必须报告实际文件数、大小、未验证项和原因。

记录执行环境、峰值内存、线程/连接数量、吞吐和失败情况。大文件仍流式处理；没有执行超过 2 GiB 的验证就不声称验证了该上限。不得把测试环境吞吐承诺为生产性能。
