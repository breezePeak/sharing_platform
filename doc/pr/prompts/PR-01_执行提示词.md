## 本阶段要交付的结果

把现有工程补齐为一个能连接 PostgreSQL、登录并打开管理页面、执行自动化测试、打包独立启动的 Java 单体。完成后，开发者按照 README 在隔离环境准备数据库、设置参数、执行命令，就能复现启动。此阶段不实现业务传输。

## 一、确认现有基础，再做缺项

检查 `sharing_platform/pom.xml`、`com.siwei.App`、现有配置、迁移、模板、测试、Wrapper 和 CI。先给出已有/缺失的简要对应关系，然后直接修改缺项；已经能通过验证的部分保留，不重新生成工程。

四份 `doc/00`—`03` 基线只做差异核对：必须保留 FTP/SFTP、统一任务入口、多监听、页面、回执和 PostgreSQL 要求。旧稿与用户后来修改冲突时，保留后来已确认内容，不用整文件覆盖。

## 二、落实构建和技术栈

使用同一 Java 应用提供 MVC 页面、静态资源和后续 API，页面采用已有 Thymeleaf 方案；持久化沿用 Spring JDBC + Flyway。Java 21 是原任务书的实施默认值。先检查仓库已落地的版本，不因旧稿写了 Spring Boot 4.1.2 就强制回退或降级；确需调整依赖时，记录原因、固定实际可解析版本并运行验证。本轮不追求“升级到最新”。

补齐 Web MVC、Thymeleaf、参数校验、JDBC、Flyway、PostgreSQL 驱动、最小安全控制、健康检查和测试所需依赖。Flyway 数据库模块与核心版本对齐。将仍存在的 JUnit 3 示例迁移到当前测试体系，不同时保留重复的示例测试框架。

提供 Windows/Unix Maven Wrapper，配置可执行 JAR；构建不依赖 IDE、Node/npm 或单独的前端服务。CI 要执行编译、单元测试、页面测试和 PostgreSQL 集成测试。

## 三、把 PostgreSQL 接入做实

1. 提供 local、test、prod 配置。数据库地址、用户名、密码由环境或外部配置提供，不提交真实口令。缺配置、连接失败或迁移失败应给出明确诊断，不回退到内存数据库。
2. PostgreSQL 主版本未由用户指定。已有部署约定就沿用；未指定时选定开发测试版本，明确记录为实施选择，并列出目标环境仍需核对的版本，不能声称已验证生产环境。
3. 测试使用隔离实例或显式测试库，启动测试前校验连接目标。测试清理只能作用于已确认的测试对象。
4. 增加最小 Flyway 迁移与真实仓储读写测试。已有实际基础表就复用；确无基础表时可按原任务书使用必要的系统元数据表验证迁移，不提前建连接、任务、清单、监听等后续业务表。
5. 验证空库初始化、同库重复启动、增量迁移，以及写入记录后停止并重新启动应用仍可读取。已经执行过的迁移不原地修改，用下一版本脚本修正。

## 四、提供可访问的页面和最小管理保护

实现 `/login`、`/services`、`/config`、`/tasks` 和共用布局。各页面用中文标题、导航、表单反馈和真实空状态；尚未实现的功能显示“尚未配置/暂无记录”，不填随机服务、模拟进度或成功任务。

一个管理员账户从外部配置初始化，缺少必要凭据时明确报错。管理页面需要登录，状态修改表单保留 CSRF；外部 API 的无状态认证边界可以预留，本阶段不伪造传输接口。

静态资源放在同一工程，避免依赖外部 CDN。统一错误页和日志关联标识；健康检查不泄露数据库口令、环境变量、完整堆栈或文件目录。

## 六、实施边界与验证重点

本阶段只交付工程基础，不实现 FTP/SFTP 连接管理、文件传输、任务引擎、监听和通知。不要以未来会用为由先造几十张表或空模块。

完成代码后，在 `sharing_platform/` 执行现有 Wrapper 的 `clean verify`；Windows 使用 `mvnw.cmd`。再用实际产物执行 `java -jar` 验证，不只运行 IDE。下表每项都要给出实际结果；数据库未能连接时，保留代码和复现命令，但数据库相关项必须标为未验证。
