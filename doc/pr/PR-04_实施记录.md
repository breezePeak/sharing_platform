## 已实现

- 开放 PUSH；复用 PR3 的任务幂等、原 XML/JSON 入口、工作池及 PRECHECK/COMPLETE 通知。新任务在受理时固定 endpoint 修订、通知地址和本地源根目录。`platform.transfers.push-intake-enabled=false` 只停止新 PUSH 受理，不停在途执行。
- V4 增量迁移保存固定文件、目录、大小、SHA-256、源修改时间、已上传及已验证进度、目标路径和发布意图。预检拒绝只产生 PRECHECK 拒绝反馈；成功反馈获关联 ACK 后才写业务文件。
- FTP/SFTP 逐文件流式上传、比对上传实际读取内容及目标完整回读内容，校验后改名。整单复查源和目标集合，上传并验证 `_manifest.xml`，记录发布意图后最后发布并回读 `_READY`。发布状态不明进入 RECONCILING；重入先核查有效标记和清单，不发送矛盾的失败完成通知。
- 任务查询可见清单总数、字节数、已上传和已验证进度；文件分页返回固定清单。完成通知保留原产品全集，产品路径指向相对 `writeRoot` 的交付位置。SFTP 列表过滤协议返回的 `.` 和 `..` 条目。

示例交付位置：`targetPath/weather/taskRecordId/productId/data.bin`。任务根目录中的 `_READY` 固定为 UTF-8 文本：

```text
taskId=<taskRecordId>
manifestSha256=<64 位 SHA-256>
productCount=<原产品数>
```

`_manifest.xml` 以固定顺序列出目录与文件，例如 `<directory path="productId/empty"/>`、`<file productId="productId" path="data.bin" size="7" sha256="..."/>`；实际摘要由预检流式读取计算，不采信客户端自报值。

## 边界与回退

旧 XML 根节点、大小写及 ACK 仍是暂定样例，默认关闭；客户真实报文与接收方 `_READY` 消费规则未联调。没有上游预期清单时，只能证明观察到的固定集合。原分支当时仅按文件更新进度；本轮已补齐流内节流进度，见下方修复记录。故障注入在本地 FTP/HTTP 测试端完成，客户网络和业务接收端仍需联合验收。

回退先设置 `platform.transfers.push-intake-enabled=false`，保留处理器、在途任务、通知与已发布数据；不删除远端成果或 V4 数据。旧版本不能识别新状态时，不直接启用旧执行器。

建议 PR 标题：`feat: deliver verified FTP/SFTP push transfers`

建议正文：开放 PUSH，冻结源清单与配置快照，按 PRECHECK ACK 门槛流式传输并完整回读目标，最后用绑定清单摘要的 `_READY` 发布整单；发布意图和重入核对避免未知结果时矛盾回调。新增 V4 增量迁移、文件进度与真实双协议/数据库测试；本机 `clean verify` 81/81 通过。外部 XML/ACK 与接收消费规则待联调，故障注入与边界见实施记录。
