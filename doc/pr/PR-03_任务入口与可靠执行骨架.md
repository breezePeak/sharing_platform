## 1. 目标与阶段边界

建立两种入口共用的任务接收、幂等、状态、查询、执行领取和通知机制。业务传输由后续 PR 接入，本 PR 不用空实现返回传输成功。

生产运行中，PUSH/PULL 处理器未安装的方向返回 `503 ENGINE_NOT_READY`，不先持久化一个永远没人处理的任务。测试环境使用明确的测试处理器验证任务框架，不把该处理器装配到生产。

## 2. 任务入口与鉴权

实现公共约定中的新任务和查询接口。callerId 由认证身份取得；调用方仅能使用已授权 endpoint、源/目标根目录、监听/来源和固定通知配置。接口禁止接受任意主机、口令、回调 URL。

区分外部 taskId 与内部 taskRecordId。保存来源、入口类型、方向、规范化请求摘要、必要原始报文、配置快照、时间、阶段、错误和版本号。原报文限制长度并脱敏，按访问权限保留，不写入普通日志。

缺少可识别任务号、认证失败、报文无法解析等同步拒绝。已能受理的业务任务，其文件数量、路由和源文件检查由具体预检查处理器反馈；不能把“请求持久化成功”当作“检查通过”。

## 3. 请求幂等与快照

数据库唯一键为 `(callerId, external_task_id)`。同键同规范化业务内容返回原任务；不同内容返回 409，不改原记录。在 PostgreSQL 使用针对该唯一键的 `ON CONFLICT DO NOTHING` 后读取并比较已有任务，或采用正确回滚边界处理唯一键冲突；遵守公共约定第 3.2 节，不能在失败事务中继续查询，也不能无条件更新旧请求，不放大为第二个执行。

跨 XML/JSON 统一成同一内部命令。规范化字段包含方向、产品集合、原路径解释和目标选择，忽略 XML 空白/属性顺序等非业务差异。重复请求使用最初记录的默认值和路由快照比较；后台配置变化不重新路由原任务。

快照至少覆盖 endpoint 版本、协议、受控目录、稳定接收方/交付范围、通知契约、来源规则与秘密版本引用。受理后编辑配置不让在途任务换协议、换地址或换校验模式。

## 4. 执行与状态基础

实现集中状态迁移服务、任务仓储、有界执行器、数据库原子领取和可重试任务的 nextRunAt。HTTP 线程只做接入事务，不执行扫描/哈希/上传。线程池满时任务留在持久化队列，不能丢任务或无限创建线程。

任务执行、通知、验收分维度保存。状态更新有前置状态、版本/领取身份校验，重复事件不倒退终态。不要为状态枚举引入外部工作流系统。

任务查询分页返回产品/文件/交付摘要；文件明细走分页接口。未冻结清单时总字节数为未知，不填 0 冒充空任务。内部失败异常分类为网络临时错误、权限/路径、配置、源变化、校验不符、发布未知等，保留可定位原因。

## 5. 持久化通知

实现 notification/outbox 记录：notificationId、任务/交付关联、阶段、协议、接收方配置快照、固定报文、内容摘要、发送次数、nextAttemptAt、状态、ACK 和最后错误。

阶段结果与通知一起提交；通知执行器分批领取、发送、验证关联 ACK、更新结果。超时及响应丢失按同编号/同报文重发。一个阶段只有一份有效结果通知，禁止同任务同时新增含义矛盾的成功/失败通知。

发送有超时与有限退避；超过自动次数后保留 NEEDS_ATTENTION。发送 HTTP 请求时不持有业务长事务。验证 ACK 身份/关联字段；错误任务号、错误通知号或仅返回 2xx 不能在未约定情况下标送达。

## 6. 旧 XML 适配与暂定契约

保留旧任务通知单、doAsk、doComplete 的适配边界。已知规则必须落实：fileCount=product 数量；product 为产品包；产品 ID 的原文长度约束；rejectrason 原拼写；doAsk 0/1；doComplete 0/1/2；完成单保留原产品全集。

实际 XML 样例、根节点、ProductList/productList 唯一结构、提交方式和 ACK 未全部确定。把开发用样例放入 `doc/contracts/provisional/` 并标注“待联调”，配套测试只能证明该暂定契约。不要同时输出两份产品列表，不声称已与客户 XML 兼容。

正式旧接口配置只有在契约样例确认并纳入回归后启用。新 JSON 入口及内部业务链可以独立推进。旧适配不能把新增 endpointId 硬塞进原 XML；通过调用方/type 唯一路由解析到已配置服务。

## 7. 修改与交付

新增 transfer 核心、统一 API、XML 适配、notification、仓储迁移和测试；数据库优先包含任务、必要产品明细、通知及关联记录。清单/文件明细由 PR-04 增量补齐，来源/交付由 PR-05 补齐。

新增 `doc/contracts/` 中的接口契约、JSON 请求/响应和暂定 XML 样例，以及只在测试启用的 HTTP 接收端。所有路径和字段在此处锁定，后续 PR 不各自另起命名。

## 一、落实任务接口和内部命令

新增入口按既有方案使用 JSON，保留旧 XML 适配层。实现以下接口：

| 接口 | 本阶段行为 |
|---|---|
| POST /api/transfers/tasks | 认证、参数及授权校验、幂等、可执行能力检查、事务受理 |
| GET /api/transfers/tasks/{taskRecordId} | 查询有权限的任务、执行/通知/验收状态、阶段与错误 |
| GET /api/transfers/tasks/{taskRecordId}/files | 分页查询已存在的文件明细；未产生清单时明确说明，不生成虚构文件 |
| 旧 XML 任务入口 | 独立协议适配到同一内部命令，不再写一套接入业务 |

统一内部命令区分 callerId、外部 taskId、内部 taskRecordId、direction、endpointId、数据范围和配置引用。callerId 从服务端认证取得，不接受请求体自行冒充调用方。请求不得携带任意主机、口令或回调地址绕过管理员配置。

本 PR 在 `doc/contracts/` 固定字段、方向参数、请求示例和错误示例；沿用已确定字段。未最终确定的字段属于实施契约，不宣称是原接口已有要求。

响应语义：新任务提交成功后返回 202；同键同内容返回 200 和原任务；同键不同内容返回 409；无效请求 400；认证/权限失败 401/403。对尚未安装真实 PUSH/PULL 处理器的新任务返回 `503 ENGINE_NOT_READY`，不留下永远无执行者的受理任务。测试处理器仅允许在测试配置启用。

## 二、设计最小持久化结构，并用 PostgreSQL 约束防重

复用已有模型，增量保存以下逻辑记录，不要求机械地一项一张表：

1. 任务：callerId、externalTaskId、taskRecordId、入口、方向、规范化业务内容及指纹、配置快照、状态、阶段、时间、错误、nextRunAt、版本/领取身份。
2. 产品或数据单元明细：保留原提交集合和关联。物理文件清单后续 PR 再补，不提前伪造。
3. 通知：notificationId、关联任务/交付、阶段、协议、接收方快照、固定报文及摘要、尝试次数、下次发送时间、状态、ACK 和错误。

数据库建立 `(callerId, externalTaskId)` 非空唯一约束。并发提交时使用正确的冲突处理和事务边界；不能只先查询再插入，不能无条件更新已有任务，也不能在已失败事务中继续读。

实现统一规范化：忽略 XML 格式空白等非业务差异，保留方向、产品范围、源路径解释、目的地和交付语义差异。等价 XML/JSON 进入同一指纹逻辑。

已存在的请求用其原配置快照解释默认参数，再比较是否等价；配置被编辑后重放旧请求，不改原目标、不产生第二次执行。同号不同内容要拒绝，保留原记录不变。

快照覆盖 endpoint/规则版本、协议与目录、接收方、通知协议和秘密版本引用。口令不进入明文快照。原始报文限长、受控保存并避免写入普通日志。

## 三、实现受理、执行、状态更新的完整顺序

受理：校验认证和引用权限 → 查询/竞争幂等记录 → 检查新任务处理能力 → 保存任务与初始状态 → 事务提交 → 返回受理结果。提交失败不能返回 accepted=true。

执行：后台扫描到期记录 → 用前置状态和版本/领取身份原子领取 → 提交短事务 → 在有界线程池执行处理器 → 用同一领取身份提交结果。线程池无容量时保留持久化排队状态，不丢任务或无限建线程。

状态更新集中在统一服务，至少分开执行、通知和拉取验收。重复事件不倒退终态，旧执行尝试的迟到写回必须被拒绝。扫描、哈希、文件 I/O 和 HTTP 调用不占用长数据库事务。

查询返回真实数据。未冻结清单时文件/字节总量是未知，不用 0 伪装空任务；任务关联和明细分页。错误至少能区分临时网络错误、路径/权限、配置、源变化、校验失败和发布待核对。

## 四、实现可恢复的通知队列

阶段结果与待发通知在同一数据库事务保存。相同阶段同一结果重入时复用原通知，不能产生两份矛盾结果。

通知发送器分批原子领取，事务提交后再发 HTTP；发送固定 notificationId 和固定报文字节，接收方、协议版本、关联编号不随重试变化。

按约定解析 ACK 并检查关联标识。仅收到 HTTP 2xx、错误任务号或错误通知号不能直接标 ACKED。新 JSON ACK 使用已确定的明确接收语义；旧 XML ACK 由对应契约解析。

超时、断网、ACK 丢失进入独立通知重试，保存次数、退避时间和最后错误；达到配置上限进入待处理。通知重试不得调用传输处理器，不能创建新任务或重新生成业务结果。

## 五、保留原 XML 语义，但区分暂定与已确认契约

旧接入必须保留：product 是产品包，fileCount 是产品数量；产品 ID 按原文约束校验；`rejectrason` 拼写不改；doAsk 的 0/1 和 doComplete 的 0/1/2 含义不变；完成单保留原产品全集。旧请求没有 endpointId 时，通过认证调用方/type 唯一路由。

真实根节点、ProductList/productList 结构或 ACK 尚未确定的部分，开发样例放 `doc/contracts/provisional/` 并标待联调，不同时输出两套产品列表。未确认旧契约不得直接开启生产对接，但不阻塞内部命令和新入口开发。

配置本地 HTTP 测试接收端，模拟正常 ACK、错误关联、已经接收但丢 ACK。它是测试夹具，不是客户平台已兼容的证据。
