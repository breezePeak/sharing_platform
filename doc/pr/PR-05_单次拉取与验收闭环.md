## 1. 目标

开放统一任务入口的 PULL 方向：对 FTP/SFTP 的指定文件、产品目录或受控扫描范围执行一次拉取，完成就绪判断、版本去重、下载、校验、待验收发布、通知和有效回执处理。单次调用不创建长期监听。

## 2. 来源规则与单次任务

来源配置至少含稳定 sourceId、endpoint、源根/范围、unitType、产品目录层级/文件匹配、就绪规则、校验级别、落地目标、业务接收方、访问映射和通知契约。先提供最小来源配置，PR-06 为其增加 listenerId/扫描周期关联，不换来源身份。

unitType 明确为 FILE 或 PACKAGE_DIR，不按后缀猜测。源的压缩包按普通文件传输，除非来源已有明确结构检查规则，不自动解压。

当前尚未就绪的 API 任务进入 WAITING_SOURCE，由任务自己的 nextRunAt 重查直至就绪或等待处理；此重查属于本次任务生命周期，不生成永久 listener。若引用 listenerId，由 PR-06 接入后校验 endpoint 关联及继承权限。

## 3. 候选、版本与交付去重

发现后立即持久化候选。有效扫描中集合/属性变化时更新候选并重置稳定次数；失败或部分扫描不增加稳定次数。满足来源就绪条件后再冻结 sourceVersion、固定本次文件集合和源端校验基准。

优先使用源端不可变版本或绑定清单摘要；大小/修改时间属于弱识别，记录 versionBasis 和强弱，不夸大覆盖发现能力。

实现公共约定的交付唯一键和原子领取，去重范围包含稳定交付位置、接收方和要求的校验规则。正在下载、通知重试、待验收或已接受的相同交付应复用并建立任务关联；不能因新 API taskId 又下载一次。不同消费方/落地目标分别交付。

一个任务范围有多个数据单元时分别分配/关联 transferId，逐单元独立处理。未就绪单元不妨碍其他已就绪单元；任务展示每项状态。所有必需单元验收成功才为整体成功；尚有处理中单元时保留处理中/部分失败信息，全部结束且存在最终失败时聚合为失败。无新数据明确 NO_NEW_DATA，不构造空交付。

## 4. 下载与技术检查

在 `tmp/transferId/` 隔离下载，按固定集合执行。写入完成且关闭后检查实际落盘大小；HASH 模式对落盘实际文件流式计算摘要并与绑定源版本的 expectedHash 比较。BASIC 保存 actualHash 供追溯，但 expectedHash 为空时不能宣布 HASH 通过。

严格 HASH 缺基准时保持不可执行并给原因，不自动降级。下载后复查源版本、属性及集合；发现变化终止旧基准交付，返回新候选观察，不拼接新旧内容。

网络临时故障有限重试，首版未完成文件整文件重下。业务不合格的同一份源数据不得无限重下。控制文件和业务文件分别统计；符号链接、越界、特殊文件拒绝。

## 5. 待验收发布与结果通知

技术检查全部通过后，发布到稳定的 `pending/transferId/`。优先同文件系统受控移动；无法原子移动时使用明确完成标记和接收规则，不能暴露半成品。发布前持久化用于恢复的清单、摘要与意图，完成后保存已发布事实及待发通知。

dataLocation 必须来自配置的业务可访问映射，不直接把共享平台的本机绝对路径当作对方可访问地址。发布后直到验收/保留处置，路径和内容不变；接收方验收成功也不自动删除或移动。

成功通知含 transferId、sourceVersion、unitType、实际文件数/字节数、校验等级与真实校验信息、有效 dataLocation。最终传输失败通知含原因，不带有效 dataLocation/已通过等级，也不开始业务验收。通知失败只补通知，不重下。

## 6. 验收回执与重新交付

实现 `POST /api/sharing/pull/confirmations` 的本轮 JSON 契约，旧/其他 XML 形式仅通过显式适配接入。验证认证接收方、transferId、sourceVersion、当前交付轮次，以及该交付已经技术通过并发布。

有效成功回执转 ACCEPTED；有效失败回执转 REJECTED 并保存原因/分类。回执先于通知 ACK 到达仍正常处理，不能因本地尚无 ACK 就拒绝已经有效的验收结果。

相同回执返回已接收；冲突终态记录协议冲突不覆盖。已被新轮次替代的旧 transferId 只记历史；不同源版本的有效旧交付仍独立可验收。验收超时保持 PENDING 并记录提醒，不自动成功或把它当传输失败。

实现受控的“新交付轮次”服务方法，用于明确修复后的重新交付：新 transferId、原子更新当前轮次关联、保留历史、重新检查源基准。普通通知重试和传输内部重试不能调用它；本 PR 不需要增加任意重跑按钮。

## 7. 修改与交付

新增 pull 服务、候选/版本和交付持久化、任务-交付关联、验收接口与记录、来源最小配置及访问映射校验。复用任务、通知、协议、哈希和路径能力，避免创建第二套状态/重试框架。

## 一、建立稳定来源配置与 PULL 入参

实现最小来源配置，保存稳定 sourceId、endpoint、允许的源根/扫描范围、unitType、文件匹配/目录层级、就绪规则、校验级别、交付根目录、接收方、业务访问映射、通知协议和配置版本。

unitType 明确为 FILE 或 PACKAGE_DIR，不按扩展名猜测；压缩包按普通文件复制，未配置结构规则就不自动解压。sourceId 表示稳定来源，不等同 endpointId，也不因每次请求生成新值。

统一入口按现有契约校验方向字段和授权范围，解析来源并保存快照。当前尚未就绪的 API 任务进入 WAITING_SOURCE，用该任务的 nextRunAt 重查；这属于一次任务的生命周期，不生成永久 listener。listenerId 继承在 PR-06 加入后复用这套规则。

## 二、先记录候选，再冻结版本和交付

扫描或定位数据时立即保存候选、观察时间、文件集合和属性。仅完整成功的观察能累计稳定次数；属性/集合变化重置观察，部分目录失败不当作文件消失。

优先使用来源的正式清单、绑定版本的完成标记或约定发布方式；没有完成信号时按配置的稳定观察条件处理，并明确这只是就绪约定，不能证明上游生产完整。

满足就绪条件后再冻结 sourceVersion、本次文件集合和校验基准。版本优先使用不可变版本号或绑定清单摘要；仅大小/修改时间时记录弱识别依据，不承诺能发现所有同大小同时间覆盖。

新增或复用候选/版本、交付和任务关联记录。一个范围任务含多个数据单元时分别关联 transferId，未就绪单元不阻塞其他已就绪单元；明细和汇总都要能查询。

## 三、通过数据库约束执行交付去重

请求幂等继续使用 callerId + externalTaskId；交付去重另按以下业务内容规范化：

    endpointId + 规范化源路径 + 数据单元规则
    + 可比较的版本依据和值 + deliveryScope

其中 deliveryScope 包含稳定落地目标/映射、业务接收方和要求的校验规则；不包含每次生成的 transferId 子目录。不同接收方、目标或校验范围分别交付，不能合并。

同范围同版本已在下载、待补通知、待验收或已验收成功时，复用原交付并保存本次任务关联。不同 API taskId 并发命中时，用 PostgreSQL 唯一约束和原子领取保证只有一轮实际下载，不能仅用 JVM 锁或先查后插。

保留当前交付轮次的原子关联，普通传输重试和通知补发沿用原 transferId；明确修复后重新交付才创建新 transferId，并保留与上一轮关系。

## 四、下载到隔离区，检查实际落盘结果

在 `tmp/transferId/` 下载固定集合，控制文件与业务文件分开统计。校验受控路径、链接和特殊文件，不能随下载进度把新出现文件混入本轮。

每个文件关闭后核对实际落盘大小、协议完成结果，并流式读取实际文件计算 SHA-256。两种校验模式严格区分：

- HASH：必须有绑定本次源版本的 expectedHash，落盘 actualHash 与它比较；缺基准就不可执行，不降级。
- BASIC：执行约定的大小、读取结果和源前后检查；本地 actualHash 可追溯，但 expectedHash 缺失不能复制 actualHash 进去冒充比较通过。

下载后复核源版本、文件集合和可获得属性。变化时结束旧基准交付、回到新候选观察，不发布混合内容。网络临时错误按有限次数重试，首版未完成文件整文件重下；同一业务不合格数据不无限重下。

## 五、发布待验收数据并发送固定结果

技术检查全部通过后发布到稳定的 `pending/transferId/`，优先同文件系统受控移动；跨文件系统时先复制并校验，再按约定完成标记暴露数据，不让业务方读取半成品。

发布前保存清单、摘要、目标位置及恢复意图；发布后保存有效交付事实和待发通知。dataLocation 来自配置的业务可访问映射，不能直接把本机路径当成对方可访问地址。已发布路径和内容保持稳定，不在验收期间移动、覆盖或删除。

成功通知含 task/transfer 关联、sourceVersion、unitType、实际业务文件数/字节数、校验等级及证据、dataLocation。最终传输失败通知含原因，不提供有效交付位置或已通过等级，不开启业务验收。通知丢 ACK 只补原通知，不重新下载。

## 六、实现验收接口和轮次保护

实现 `POST /api/sharing/pull/confirmations`，使用已锁定的新接口契约；其他 XML 形式只能由显式适配接入。先验证认证接收方、transferId、sourceVersion、当前交付轮次，以及技术检查通过且已经发布的前提，然后事务保存回执和状态，再回复。

有效成功回执转 ACCEPTED，失败转 REJECTED 并保存原因/分类。回执先于本地收到通知 ACK 到达仍应接受；不能把 ACK 先到作为验收前置条件。

重复相同回执返回已有结果，矛盾终态记录冲突不覆盖。被同源版本新轮次替代的旧 transferId 回执只记历史；不同源版本仍有效的交付分别验收，不能一并拒绝。验收超时保持待验收并提醒，不自动成功或失败。

重新交付提供受控服务方法：核对源基准、创建新 transferId、原子切换当前轮次、保留历史。不增加任意“全部重跑”按钮。

## 七、汇总、验收和回退

所有必需单元验收成功才汇总为任务成功；某个单元成功不能带动全单成功。其他单元仍处理时保留进度和部分失败信息；全部结束且有最终失败才汇总失败。没有新增数据时明确 NO_NEW_DATA 和范围，不伪造空 transferId 或验收通知。

用真实 FTP/SFTP、PostgreSQL 和本地业务接收端执行下表。重点覆盖并发复用、错误哈希、下载时源变化、回执早于 ACK、冲突和旧轮次回执、多单元聚合以及业务访问映射。

本阶段不实现周期监听，不自动删除源或交付数据。回退时可以关闭新 PULL 受理，但保留已发出的 transferId、查询、通知和验收能力。
