| 项目 | 内容 |

## 1. 目标

开放统一任务入口的 PULL 方向：对 FTP/SFTP 的指定文件、产品目录或受控扫描范围执行一次拉取，完成就绪判断、版本去重、下载、校验、待验收发布、通知和有效回执处理。单次调用不创建长期监听。

## 2. 来源规则与单次任务

来源配置至少含稳定 sourceId、endpoint、源根/范围、unitType、产品目录层级/文件匹配、就绪规则、校验级别、落地目标、业务接收方、访问映射和通知契约。先提供最小来源配置，PR-06 为其增加 listenerId/扫描周期关联，不换来源身份。

unitType 明确为 FILE 或 PACKAGE_DIR，不按后缀猜测。源的压缩包按普通文件传输，除非来源已有明确结构检查规则，不自动解压。

当前尚未就绪的 API 任务进入 WAITING_SOURCE，由任务自己的 nextRunAt 重查直至就绪或等待处理；此重查属于本次任务生命周期，不生成永久 listener。若引用 listenerId，由 PR-06 接入后校验 endpoint 关联及继承权限。

## 3. 候选、版本与交付去重

发现后立即持久化候选。有效扫描中集合/属性变化时更新候选并重置稳定次数；失败或部分扫描不增加稳定次数。满足来源就绪条件后再冻结 sourceVersion、固定本次文件集合和源端校验基准。

优先使用源端不可变版本或绑定清单摘要；大小/修改时间属于弱识别，记录 versionBasis 和强弱，不夸大覆盖发现能力。

实现公共约定的交付唯一键和原子领取，去重范围包含稳定交付位置、接收方和要求的校验规则。正在下载、通知重试、待验收或已接受的相同交付应复用并建立任务关联；不能因新 API taskId 又下载一次。不同消费方/落地目标分别交付。

一个任务范围有多个数据单元时分别分配/关联 transferId，逐单元独立处理。未就绪单元不妨碍其他已就绪单元；任务展示每项状态。所有必需单元验收成功才为整体成功；尚有处理中单元时保留处理中/部分失败信息，全部结束且存在最终失败时聚合为失败。无新数据明确 NO_NEW_DATA，不构造空交付。

## 4. 下载与技术检查

在 `tmp/transferId/` 隔离下载，按固定集合执行。写入完成且关闭后检查实际落盘大小；HASH 模式对落盘实际文件流式计算摘要并与绑定源版本的 expectedHash 比较。BASIC 保存 actualHash 供追溯，但 expectedHash 为空时不能宣布 HASH 通过。

严格 HASH 缺基准时保持不可执行并给原因，不自动降级。下载后复查源版本、属性及集合；发现变化终止旧基准交付，返回新候选观察，不拼接新旧内容。

网络临时故障有限重试，首版未完成文件整文件重下。业务不合格的同一份源数据不得无限重下。控制文件和业务文件分别统计；符号链接、越界、特殊文件拒绝。

## 5. 待验收发布与结果通知

技术检查全部通过后，发布到稳定的 `pending/transferId/`。优先同文件系统受控移动；无法原子移动时使用明确完成标记和接收规则，不能暴露半成品。发布前持久化用于恢复的清单、摘要与意图，完成后保存已发布事实及待发通知。

dataLocation 必须来自配置的业务可访问映射，不直接把共享平台的本机绝对路径当作对方可访问地址。发布后直到验收/保留处置，路径和内容不变；接收方验收成功也不自动删除或移动。

成功通知含 transferId、sourceVersion、unitType、实际文件数/字节数、校验等级与真实校验信息、有效 dataLocation。最终传输失败通知含原因，不带有效 dataLocation/已通过等级，也不开始业务验收。通知失败只补通知，不重下。

## 6. 验收回执与重新交付

实现 `POST /api/sharing/pull/confirmations` 的本轮 JSON 契约，旧/其他 XML 形式仅通过显式适配接入。验证认证接收方、transferId、sourceVersion、当前交付轮次，以及该交付已经技术通过并发布。

有效成功回执转 ACCEPTED；有效失败回执转 REJECTED 并保存原因/分类。回执先于通知 ACK 到达仍正常处理，不能因本地尚无 ACK 就拒绝已经有效的验收结果。

相同回执返回已接收；冲突终态记录协议冲突不覆盖。已被新轮次替代的旧 transferId 只记历史；不同源版本的有效旧交付仍独立可验收。验收超时保持 PENDING 并记录提醒，不自动成功或把它当传输失败。

实现受控的“新交付轮次”服务方法，用于明确修复后的重新交付：新 transferId、原子更新当前轮次关联、保留历史、重新检查源基准。普通通知重试和传输内部重试不能调用它；本 PR 不需要增加任意重跑按钮。

## 7. 修改与交付

新增 pull 服务、候选/版本和交付持久化、任务-交付关联、验收接口与记录、来源最小配置及访问映射校验。复用任务、通知、协议、哈希和路径能力，避免创建第二套状态/重试框架。

## 8. 验收与测试

| 编号 | 场景 | 预期 |
|---|---|---|
| 05-T01 | FTP/SFTP 分别 FILE/PACKAGE_DIR 单次拉取 | 内容和结构正确；不创建永久监听 |
| 05-T02 | 源暂不就绪后变稳定 | 同一 API 任务重新检查并继续，不每次创建新交付 |
| 05-T03 | HASH 缺基准；BASIC 仅有本地 hash | 前者不可执行；后者不标 HASH 通过 |
| 05-T04 | 同大小坏内容与已知源 hash 不符 | 技术检查失败，不发布到待验收区 |
| 05-T05 | 下载期间源版本/集合改变 | 原交付不发布，不混合新旧数据 |
| 05-T06 | 相同交付通过不同 API taskId 并发命中 | 一个下载/交付，两任务能关联查询同一结果 |
| 05-T07 | 相同源交给不同消费者/目标 | 各自交付，不被错误去重 |
| 05-T08 | 下载结束、通知 ACK 丢失 | 字节 100% 仍待验收；只补通知不重下 |
| 05-T09 | 验收成功先于通知 ACK | 正常接受；不会因 ACK 缺失重新传输 |
| 05-T10 | 重复、相反、伪造来源、未发布的成功回执 | 重复幂等，其余冲突/拒绝，不覆盖状态 |
| 05-T11 | 新轮次后旧回执到达；不同源版本分别回执 | 旧轮次不污染新轮次，不误拒另一个有效版本 |
| 05-T12 | 多单元仅一个验收成功 | 不把整个任务标成功；逐项可查 |
| 05-T13 | 验收超时或业务质量失败 | 保持待验收/明确拒绝，不无限重下同一源 |
| 05-T14 | 最终传输失败或无新增数据 | 失败通知无有效交付位置；无数据不伪造验收 |
| 05-T15 | 本地位置对业务方不可访问 | 配置/交接检查明确失败，不把本机路径当成功交付 |

真实 FTP/SFTP、PostgreSQL 加本地测试接收端验证上述链路；交付唯一约束、回执幂等和状态事务必须在 PostgreSQL 上验证。外部业务平台的访问及回执仍单独联调。

## 9. 回退

关闭 PULL 新请求；已发布待验收数据、回执和通知必须保留，并继续支持已经发出的 transferId 查询及验收。不能通过回退使业务方正在访问的位置消失。
