## 1. 目的与依据

本文件规定共享平台、业务平台、源数据生产方及 FTP/SFTP 管理方分别承担的工作，以及推送、拉取的成功标准。开发、联调和验收均应使用相同口径。

设计依据包括：

1. 用户提出的推送流程：接收任务，检查文件和链路，反馈可执行或拒绝，完成传输后上报结果。
2. 用户提出的拉取流程：定时发现新数据，检查就绪和完整性，下载后通知业务平台，取得平台验收回执。
3. 用户提供的《2.1 调度系统与数据云共享子系统接口设计》，其中推送任务通知单、反馈单和完成单分别对应 2.1.2、2.1.3、2.1.4。
4. 本次讨论补充的首版目录、校验、发布、幂等和故障处理规则。
5. 用户最新明确要求：FTP/SFTP 服务列表可配置，提供接口执行推送或拉取，支持多个拉取监听目标，提供配置、当前服务、进度详情和状态页面，使用 Java 且不做前后端分离。
6. 用户后续补充：“计划使用postgre”。数据库选型按 PostgreSQL 记录，具体主版本未指定。

用户事实、原接口约束、设计建议与待确定事项按 [00_事实需求依据.md](00_事实需求依据.md) 分开管理。前述技术细则属于当前设计基线，不能反向当作用户逐项指定或外部系统已经支持的证据。

原接口已有要求与本设计补充规则的性质不同。本文不将新增目录含义、拉取接口或完成标记描述为对方系统已经实现的能力。现有三张 XML 的实际样例尚未提供，字段大小写和即时响应格式需要在联调前落定。

## 2. 系统范围

### 2.1 首版交付范围

共享平台提供两条业务链路：

- 推送：业务平台通过已有 XML 接入或建议的统一任务入口下发任务，共享平台从配置的本地源目录读取产品，通过 FTP 或 SFTP 推送到配置的目标服务，反馈预检查和执行结果。
- 拉取：多个监听目标按各自配置定时扫描源 FTP/SFTP 服务；对外接口也可发起单次拉取。两类触发共用发现、去重、下载、技术检查、平台通知和验收回执流程。

两条链路共用配置管理、文件校验、传输执行、任务记录、日志、通知补发和恢复。Java、非前后端分离、PostgreSQL 已明确；S7 固定 JDK 11、页面无需登录、直接连接且不使用 Docker，S8 指定 JPA 并禁止 Spring Security。页面和 HTTP 接口由同一应用提供；具体框架、模板引擎及 PostgreSQL 版本仍为实施选择，表结构由 Flyway 管理。

### 2.2 内容处理范围

共享平台负责文件与目录的技术交付，包括按约定识别数据单元、检查路径和文件集合、核对字节数及校验值、控制临时成果和有效成果的发布。

产品生产、影像处理、业务内容修复，以及影像区域、坐标、产品用途等业务有效性判断，由生产方或业务平台承担。已配置的必需文件规则、结构检查规则可以由共享平台执行，但必须有明确的预期规则作为依据。

### 2.3 服务、监听和任务的边界

以下概念用于把用户提出的“服务”落实为可管理对象，属于设计定义。

| 对象 | 标识建议 | 边界 |
| --- | --- | --- |
| 远端服务连接配置 | endpointId | 一个 FTP 或 SFTP 连接对象，保存协议、地址、凭据引用、允许目录和启用状态；可被多个监听和任务引用 |
| 拉取监听目标 | listenerId | 引用一个远端服务，配置源目录、扫描规则、周期、就绪规则和本地交付位置；一个远端服务可以配置多个监听目标 |
| 传输任务 | taskId | 一次具体推送或拉取，记录触发来源、协议、源目标、文件进度、执行结果和通知状态 |
| 拉取交付轮次 | transferId | 继续沿用既有定义，用于关联一次拉取交付和平台验收回执 |

原拉取文档中的 sourceId 继续表示稳定的数据来源及规则标识，与监听配置建立固定映射，不等同于仅保存连接参数的 endpointId。监听配置编辑不能清空已处理数据记录或将已有交付改成新版本。

API 单次拉取只执行本次任务，不自动创建长期监听。建议由触发来源字段区分 API 与 SCHEDULE，执行器复用同一条传输链。不同监听目标独立保存扫描结果和时间；一个目标异常不应阻塞其他目标，实际并发上限由配置控制。

同一来源及交付范围内遵循既有版本去重规则。对于同一 endpoint 的多个监听目录重叠或 API 与监听命中同一文件，建议按规范化远端路径、可比较版本和相同交付范围识别重复。交付范围包括稳定的本地目标、业务接收方及所需校验规则；不同范围不能被错误合并。源版本记录可以共用，交付复用须再比较这些条件，并通过规范化交付键的唯一约束和原子领取避免跨监听并发重复执行。具体跨目标策略应在详细设计中落定。

### 2.4 页面职责与 Java 交付方式

用户明确要求配置页面、当前服务展示、进度详情和状态；具体页面数量属于设计选择。首版建议三个主要页面：

| 页面 | 内容 |
| --- | --- |
| 配置页面 | 远端 FTP/SFTP 服务列表与连接配置；多个拉取监听目标的目录、周期、就绪和校验规则 |
| 服务运行页面 | 远端服务启用和最近连通情况、监听目标扫描状态、最近与下次扫描时间、当前任务入口 |
| 任务详情页面 | 本次任务的协议、源目标、阶段、字节及文件进度、当前文件、耗时、速度、错误、通知和验收状态 |

页面和业务处理属于同一个 Java Web 项目和部署应用。页面局部刷新或状态查询不等于独立前端工程；前端框架、刷新方式和框架版本均不能据此写成已确认需求。

配置启停与任务暂停取消是不同操作。建议停用服务或监听后停止创建新任务，在途任务按原配置快照处理；是否需要主动取消、暂停和恢复，仍属待明确功能。被历史任务引用的配置不得通过直接删除破坏历史记录。

## 3. 参与方与责任

同一单位可以承担多个角色，但每项责任都需要明确承接方。

| 事项 | 主要责任方 | 责任说明 |
| --- | --- | --- |
| 产品生成 | 源数据生产方 | 生成所需产品及辅助文件，对产品组成和业务内容负责 |
| 源数据就绪 | 源数据生产方 | 明确何时允许传输；在约定的交付窗口保持该版本稳定 |
| 推送任务下发 | 业务平台 | 提供唯一任务号、产品列表、正确的产品路径和产品数量 |
| 请求校验与任务去重 | 共享平台 | 校验请求、持久化任务、避免相同任务重复执行 |
| 推送预检查 | 共享平台 | 检查任务范围、源文件、传输路由及目标 FTP/SFTP 服务的实际传输和校验能力 |
| FTP/SFTP 服务条件 | FTP/SFTP 管理方 | 提供地址、账号、目录、权限、网络和存储条件，维护服务可用性 |
| 传输执行和技术校验 | 共享平台 | 按固定基准传输并记录证据，处理传输重试和未知结果 |
| 推送整单发布 | 共享平台与接收方 | 共享平台最后发布有效完成标记；接收方按标记读取整单 |
| 拉取前就绪检查 | 共享平台 | 根据该来源约定的完成信号或稳定性条件决定是否开始下载 |
| 拉取后技术检查 | 共享平台 | 核对本地文件、来源版本、文件集合及可用的源端校验依据 |
| 拉取后业务验收 | 业务平台 | 读取数据，检查业务完整性与可用性，返回明确验收结果 |
| 接口接收确认 | 接口提供方 | 保存收到的消息后返回可关联的接收确认，支持重复请求 |
| 通知补发 | 通知发送方 | 保存通知并按规则重试，避免因响应丢失重复执行数据传输 |

## 4. 数据单元、路径与配置边界

### 4.1 推送的数据单元

下表属于本设计补充约定，原文仅说明一个 product 代表一个数据包。

| 项目 | 首版约定 |
| --- | --- |
| product | 一个独立产品目录；单个 ZIP、TIFF 等文件也放入产品目录 |
| productPath | 相对于源根目录的产品目录路径 |
| productName | 产品显示名称，不作为实际文件名拼接依据 |
| fileCount | 本任务 product 数量，即产品包数量 |
| 实际文件范围 | 递归纳入产品目录中的普通文件，按固定传输清单交付，保留相对目录结构 |
| 源目录就绪 | 下发任务代表生产方确认该版目录已经生成完成 |
| 源目录冻结 | 从提交任务到任务结束，生产方保持该版本不增删、不替换、不修改 |
| 特殊文件 | 首版拒绝符号链接和特殊文件；临时文件、零字节文件按明确的产品规则处理 |

源路径由“源根目录＋productPath”确定。规范化和解析后必须仍处于允许的根目录内；存在越界、重复纳入或目标文件名冲突时拒绝执行。

### 4.2 拉取的数据单元

每个来源配置固定采用一种数据单元模式：单文件模式或目录产品包模式。共享平台按配置解析，不能在同一来源中临时猜测某个路径究竟代表文件还是产品包。

目录包有源端预期清单时，按清单检查；没有预期清单时，只能固定观察到的文件集合，无法证明上游没有漏生成未知文件。该限制需要与业务平台的验收责任一起明确。

### 4.3 传输路由

| 方向 | 配置和定位规则 |
| --- | --- |
| 原 XML 推送路由 | 来源系统＋产品 type 必须匹配唯一启用配置，取得源根目录、endpointId 和目标根目录 |
| 统一接口推送路由 | 建议通过 endpointId 选择已配置且有权使用的服务；源和目标范围仍受配置约束 |
| 推送目标 | 按服务配置的协议使用 FTP 或 SFTP，保存连接及校验规则快照 |
| 推送任务目录 | 目标根目录/来源系统编码/taskId/ |
| 推送产品目录 | 任务目录/productId/；产品内部文件保留相对路径 |
| 推送控制文件 | 任务根目录下的 _manifest.xml 和 _READY，与各产品目录分开 |
| 定时拉取来源 | listenerId 引用 endpointId，并关联稳定 sourceId、扫描范围、数据单元和交付规则 |
| 单次接口拉取 | 指定已配置远端服务和受控路径，或引用监听/来源规则；不自动创建常驻监听 |
| 拉取落地 | 使用任务或交付编号隔离临时区和待验收位置 |

使用外部标识构造目录前应校验或安全编码路径片段。账号、目标根目录和回调地址由配置管理，不通过未知 XML 字段临时指定。

任务创建后保存所使用的路由和规则快照，包括 endpointId、FTP/SFTP 协议、来源或监听关联及触发方式。配置调整作用于后续任务，不在已有任务执行中切换协议、目的地或校验标准。

完成单 productPath 在本设计中约定为相对于目标根目录的已分配产品目录路径。成功任务中的该路径可用于交付定位；失败任务中的路径仅用于诊断，不表示成果有效。此含义属于补充对接约定。

### 4.4 FTP 与 SFTP 的能力边界

两种协议共用任务、文件清单、结果和发布规则，连接与文件操作由各自适配器执行。

| 项目 | FTP | SFTP |
| --- | --- | --- |
| 连接和身份 | FTP 登录以及实际控制、数据通道探测 | SSH 连接、服务器主机密钥校验、用户认证和 SFTP 会话 |
| 文件属性和列举 | 使用实际支持的目录及 SIZE 等能力 | 使用 SFTP 目录和文件属性操作 |
| 传输方式 | 统一约定二进制传输，按配置使用数据连接方式 | 按 SFTP 文件读写接口传输字节，不套用 FTP 的 TYPE 或被动模式 |
| 严格内容校验 | 实测远端 SHA-256，或全量回读 | 实测服务端及客户端支持的校验能力，或全量回读；不默认支持通用远端 SHA-256 |
| 整单发布 | 验证所需文件操作后采用清单与有效完成标记 | 使用协议实际支持的操作实现相同发布约定，不假定所有服务器都有相同重命名扩展 |

SFTP 在 SSH 传输上执行文件操作，参见 [OpenSSH sftp 手册](https://man.openbsd.org/sftp)。主机身份核对、凭据保护属于本设计的接入要求；具体密码或私钥认证配置由目标服务条件决定。

## 5. 完整性的范围和依据

### 5.1 四种不同的判断

| 判断 | 谁提供依据或结论 | 共享平台承担的检查 |
| --- | --- | --- |
| 源产品是否生产齐全 | 生产方及其预期清单、产品规则 | 执行已约定规则；不猜测未知的必需文件 |
| 源数据是否可以开始传输 | 生产方的发布约定，或来源配置的稳定性规则 | 执行拉取条件或推送就绪检查，并记录采用的依据 |
| 文件是否完整传到目标 | 固定的大小和内容校验基准 | 对实际传输内容及目标内容进行验证 |
| 产品业务内容是否合格 | 业务平台 | 接收并保存验收回执，按原因交回责任方 |

### 5.2 推送的完整性承诺

共享平台预检查时自行生成并持久化“传输清单”，记录产品、相对路径、文件大小、SHA-256 和目录结构。原 XML 不要求源端新增清单文件；生产方已有预期清单或产品结构规则时，可以增加核对。

传输清单描述本次固定的文件集合。它不等同于生产方的“应生成成果清单”。如果生产方漏生成文件且没有提供预期规则，计算哈希不能发现这个未知缺项。

严格推送必须满足：

1. 任务中的全部产品均纳入固定传输清单。
2. 目标业务文件集合和目录结构符合该清单。
3. 每个文件的字节数与清单一致。
4. 每个文件的目标实际内容 SHA-256 与固定基准一致；上传时也核对实际读取内容。
5. 整单全部通过后才发布有效完成标记。

目标端优先使用准确大小查询和远端 SHA-256；不具备远端哈希能力时，全量回读实际目标文件并统计字节数、计算 SHA-256。两种方式均无法执行时，该链路不满足本版严格推送条件，预检查拒绝，不能静默降级。

远端校验能力依赖 FTP/SFTP 服务端和客户端的实际支持，详见 [WinSCP 远端校验能力说明](https://winscp.net/eng/docs/ui_properties#checksum)。哈希用于发现相对于基准的内容变化，详见 [NIST Secure Hash Standard](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)。

### 5.3 拉取的校验等级

每个来源配置明确所要求的校验等级，执行记录保存实际采用的方法。

| 等级 | 条件 | 成功判定的范围 |
| --- | --- | --- |
| BASIC | 源端没有可比较的内容校验基准，但满足已约定的基础拉取条件 | 完成响应、实际字节数、源属性和可执行的结构检查通过，进入待业务验收 |
| HASH | 有与源版本绑定的源端 SHA-256 或等效的可靠基准 | 基础检查和源端基准哈希比对通过，进入待业务验收 |

共享平台对下载文件自行计算的哈希可以用于留档及后续本地一致性检查，但没有源端比较值时，不能标记为 HASH 比对通过。配置要求 HASH 而基准缺失时，保持不满足条件或失败，不能自动改为 BASIC。

源文件大小、修改时间连续不变，只说明观察窗口内未发现变化，不能严格证明生产结束。目录包中各文件暂时稳定，也不能证明后续不会再生成新文件。

## 6. 源版本、重复任务和交付编号

| 标识 | 含义和约束 |
| --- | --- |
| 来源系统＋taskId | 推送任务唯一键；原 XML 与统一入口规范化后共用幂等判断；同内容返回已有状态，不同内容冲突 |
| sourceId＋sourcePath | 拉取待就绪候选的观察关联键；属性变化时更新候选并重置稳定次数 |
| sourceId＋sourcePath＋sourceVersion | 拉取就绪后冻结源版本的识别键；交付复用另需匹配稳定目标、接收方及所需校验规则，相同范围内不得重复建交付 |
| 源端版本或清单摘要 | 优先作为拉取版本依据，必须与当前发布内容绑定 |
| 大小＋修改时间等属性 | 无强版本信息时的兼容识别依据；同内容长度和时间不变的覆盖可能无法识别 |
| transferId | 一次拉取交付尝试的唯一编号；通知补发沿用原编号，修复后重新交付使用新编号并关联原发现记录 |

发现即登记候选，满足就绪和校验基准条件后，在创建 transferId 前固定正式版本。待就绪记录需要在后续扫描中继续检查；候选属性变化时刷新观察，不为每轮变化创建交付任务。已冻结或已交付的版本不得原地修改。失败记录进入原记录的重试或处置流程，不得每次扫描都创建新的失败任务。

发现版本的依据强弱与内容校验等级独立记录。弱版本发现规则不能保证识别所有覆盖，但若本轮确实完成源端哈希比对，内容校验仍可记录 HASH；没有内容比较基准时记录 BASIC。

推送重试继续使用原固定清单。源内容变化后不重新生成基准并沿用原任务放行；生产方修复后应形成新的交付任务。

拉取回执必须关联当前交付编号及对应源版本。迟到回执可以保留到历史记录，但不能覆盖新一轮交付状态；同一交付的终态不能因重复或冲突回执被静默回退。

## 7. 成功标准与接口含义

用户要求通过接口执行 FTP/SFTP 推送或拉取。建议统一任务入口为 POST /api/transfers/tasks，通过 direction=PUSH/PULL 和 endpointId 选择方向及已配置服务；具体 URL、报文和参数为建议。原 XML 接入继续兼容原字段，经适配后进入同一执行链。统一入口的推送分支绑定调用方通知配置，保留预检查反馈及最终结果通知；拉取分支保留拉取结果通知及平台验收回执。通用通知报文和 ACK 细节需另行约定。状态查询用于补充查看和异常核对，不自动取代结果通知。

### 7.1 推送

| 节点 | 成功的含义 | 依据 |
| --- | --- | --- |
| 接收任务通知单 | XML 达到接入条件且任务已持久化 | 本设计补充即时接收规则 |
| doAsk result=0 | 一致性和执行条件检查通过，任务可进入执行 | 原接口 2.1.3，补充执行前检查范围 |
| doAsk result=1 | 预检查拒绝，反馈具体原因 | 原接口 2.1.3 |
| doComplete status=0 | 全部产品通过约定传输校验并完成有效发布 | 原接口 2.1.4，补充发布规则 |
| doComplete status=1 | 已进入执行的整单最终失败，全部成果按无效交付处理 | 原接口 2.1.4 |
| doComplete status=2 | 作废删除业务状态 | 原接口 2.1.4；实际删除范围仍需单独约定 |
| 推送流程关闭 | 确定的执行结果已经保存，所需业务通知已取得接收确认 | 本设计补充闭环规则 |

doAsk 成功不精确代表已经传出了第一个文件字节。实际运行状态由共享平台记录；需要外部精确获知开始时间时，可另行约定查询或事件。

预检查拒绝默认通过 doAsk 结束，不再发送执行完成单；如对方要求所有拒绝任务另发完成单，需要明确补充协议。失败完成单保留原任务全部 product，fileCount 不改为成功数量。

推送成功范围止于约定目标上的有效交付，不表示接收业务系统已经完成后续入库或业务验收。

### 7.2 拉取

| 节点 | 成功的含义 |
| --- | --- |
| 下载完成 | 文件已完整落地，完成该来源要求的技术检查 |
| 拉取结果通知送达 | 业务平台已经持久化接收本次交付通知 |
| 待业务验收 | 数据位置可访问且保持稳定，等待平台检查 |
| 验收成功 | 交付已通过技术检查并发布待验收，收到对应 transferId、源版本的明确成功结果后，才完成拉取闭环 |
| 验收失败 | 保存平台明确返回的失败原因，按责任分类处置 |
| 验收超时 | 继续为待确认，执行超时提醒或幂等补发；不能自动改为成功或重新下载 |

拉取结果通知接口和验收回执接口均为本设计新增接口，详见 [02_拉取流程.md](02_拉取流程.md)。

当前有效交付的验收回执可以先于通知发送方收到 ACK 到达。传输失败或尚未发布的交付收到成功验收回执时，记录协议冲突，不覆盖原传输结果。失败拉取通知不携带有效交付位置或已通过的校验等级，不启动业务平台验收。

### 7.3 接收确认与业务结果分开

现有文档仅说明接口“异步”，没有提供可直接实现的即时响应体。双方需要约定可关联的接收确认，接收方持久化消息后再确认；重复消息返回已有接收结果。

HTTP 202 表示已接受处理、尚未完成处理，参见 [RFC 9110 第 15.3.3 节](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。对其他成功 HTTP 状态也应按具体接口约定解释，不能把通知接收成功当成数据业务验收成功。

文件执行状态、通知状态和验收状态分别持久化。一个任务可以显示“传输成功，完成通知待补发”，或“拉取成功，待平台验收”。

### 7.4 页面状态与进度的含义

| 状态维度 | 页面表达原则 |
| --- | --- |
| 远端配置 | 启用或停用属于配置状态；最近连通正常、异常或未知属于健康检查结果 |
| 监听运行 | 分别显示启用状态、等待扫描、扫描中、异常、最近及下次扫描时间 |
| 任务执行 | 显示预检查、排队、传输、内容核验、发布、执行结果等实际阶段 |
| 通知和验收 | 显示待通知、待补发、已接收、待验收及最终验收结果，不混成传输状态 |
| 字节进度 | 已传业务字节与本轮已确定总字节对比；字节 100% 不代表目标校验、发布或业务验收已完成 |
| 总量未知 | 枚举阶段显示扫描中或总量待确定；不编造百分比 |
| 重试进度 | 重试额外网络流量不能叠加为已完成业务字节，避免超过 100% |

页面进度由后台任务记录提供。推送上传结束后仍可能处于目标回读校验；拉取下载结束后仍可能处于待平台验收。状态枚举、刷新方式和显示字段详见事实需求依据中的建议定义。

## 8. 发布和存储生命周期

### 8.1 推送成果发布

目标任务目录在有效 _READY 出现前均视为暂存成果。共享平台校验全部产品，上传并验证固定的 _manifest.xml，最后发布绑定清单摘要的 _READY。接收方仅消费标记有效且引用清单匹配的整单。

控制文件应先临时写入，再发布正式名称。不得把多个独立文件传输操作宣称为服务端整单事务。接收方如果提前读取未发布目录，就不能满足本设计的整单消费边界。

目标任务目录由本次任务独占写入；已发布成果不在原位置继续覆盖。发布响应丢失时，先核对标记和清单，结果不明就进入待核对，不盲目回报失败或重新覆盖。

### 8.2 拉取数据交接

下载临时文件不交给业务平台使用。技术检查完成后，放入平台可访问的待验收位置，先持久化当前交付和通知记录，再发送通知。

数据位置可以是双方配置的共享目录或受控读取地址。共享平台自己的本地绝对路径，只有业务平台确实能够访问时才可用作交接位置。验收期间路径和内容保持稳定。

### 8.3 保留和清理

- 推送和拉取默认复制数据，源数据保留。
- 共享平台仅按策略清理自己创建的临时文件和任务暂存成果，不删除外部来源数据或其他任务成果。
- 待验收、通知未完成、结果待核对的数据不得被普通成功清理规则移除。
- 验收失败数据保留定位信息，根据原因进入隔离或待修复状态。
- 已确认成果的保留期、归档方式和删除权限由业务要求另行确定，不能从 status=2 自动推导任意文件删除授权。

## 9. 异常责任与重试边界

| 问题 | 处理责任和行为 |
| --- | --- |
| XML 格式、任务编号或必填字段错误 | 共享平台给出明确错误；不可识别任务的请求在接入阶段拒绝 |
| 数据缺失、目录尚未生成完 | 生产方修复；共享平台报告具体产品、文件和检查结果 |
| 网络中断或暂时 FTP/SFTP 错误 | 共享平台按文件重试，默认首次尝试之外最多重试 3 次，即最多 4 次尝试，次数可配置 |
| 目标内容与固定基准不一致 | 共享平台复核源版本并有限重传，仍失败则停止有效发布 |
| 源版本变化 | 原基准不再作为可继续读取的源；不得拼接不同版本或偷偷替换清单 |
| FTP/SFTP 权限、目录或配额不足 | FTP/SFTP 管理方修复条件；共享平台返回可定位原因，不无限重试 |
| 通知超时或 ACK 丢失 | 通知发送方幂等重发，不重做已经成功的数据传输 |
| 平台暂时无法读取或自身验收服务异常 | 保留同一交付及数据位置，按双方约定等待或重试验收 |
| 本地副本损坏，需要重新交付 | 复核源版本后重新下载，以新 transferId 发起新一轮交付 |
| 源数据业务内容不合格 | 平台返回原因，由生产方修复；不反复下载相同坏数据 |
| 发布结果不明 | 共享平台查询远端标记和清单，超限转待核对并提醒，不虚构终态 |
| 平台验收超时 | 保持待确认，记录超时并提醒；不能把未回复当成验收失败或成功 |

首版重试以文件为单位。对已经验证成功且仍符合原清单的成果可以复用；不确定的半成品可以从头重传。恢复执行前要领取原任务，避免多个执行器并行写同一交付。

## 10. 对接能力和待确认项目

这些项目不阻止形成当前设计，但需要在正式联调协议中写明。不得把尚未验证的外部能力记录为已具备。

| 对接项目 | 当前设计或建议 | 原文情况 |
| --- | --- | --- |
| 推送 productPath 数据形式 | 统一产品目录 | 原文未明确目录、单文件或压缩包 |
| 源根目录与目标目录 | 原 XML 按来源＋type 路由，统一入口引用 endpointId 及受控范围 | 原任务单没有独立 FTP/SFTP 服务或目标目录字段 |
| 完成单 productPath | 相对于目标根目录的已分配产品目录路径 | 原文未明确源路径还是目标路径 |
| ProductList 与 productList | 联调前确定唯一正式结构 | 完成单字段表出现两个大小写不同名称 |
| rejectrason | 对外保持文档拼写，内部可映射规范字段 | 原反馈单字段名 |
| 接收 ACK 格式 | 明确关联编号、消息类型、已持久化接收结果 | 原文只写异步 |
| 整单失败的产品状态 | 保存原产品全集，成功、失败、未执行都有明确填写规则 | 原文只规定整单失败后全部作废 |
| 目标端完整性校验能力 | 远端大小＋SHA-256，或全量回读 | 原接口未规定 |
| 推送 _READY 消费规则 | 接收方只读取有效发布的整单 | 本设计新增 |
| 拉取来源完成条件 | 有发布信号按信号；无信号采用明确的稳定性规则 | 需要逐来源约定 |
| 拉取校验等级 | 来源配置明确 BASIC 或 HASH，保留实际校验依据 | 本设计新增 |
| 拉取首次扫描 | 默认处理当前未登记数据；建立历史基线需显式选择并记录 | 本设计新增 |
| 拉取通知和回执 | 两个新接口，交付编号幂等关联 | 原文仅提供推送接口 |
| 数据保留期与验收期限 | 根据业务数据量、处理时长和存储条件配置 | 尚无具体数值 |
| 多监听重叠与 API 重复命中 | 建议对相同来源版本及相同目标、接收方和校验要求去重，保留不同交付范围 | 具体跨目标规则尚未指定 |
| 页面组织与操作按钮 | 建议配置、运行、详情三个主要页面；暂停取消功能另行明确 | 用户已明确页面能力，未指定确切页面数量及按钮 |
| Java 实现 | JDK 11，同 Java Web 应用提供直接访问的页面及对外接口，直接连接 PostgreSQL，不使用 Docker | Java 11、无需登录、非前后端分离及 PostgreSQL 类型已明确；数据库具体版本与框架仍属实施选择 |

原文提到的三份样例 XML 应用于确认字段层级、大小写、空值形式和请求提交方式。对既有接口的语义调整以补充协议落定，不通过实现端猜测。

## 11. 开发和验收中必须保持的规则

1. 原接口 fileCount 始终表示产品包数量；拉取实际文件数使用独立字段，避免混淆。
2. 预检查生成的传输清单在同一推送任务中固定，源变化不得静默更新基准。
3. 严格推送没有目标内容验证能力时拒绝执行，不能改成只检查上传响应。
4. 拉取本地自算哈希不冒充源端比较基准；BASIC 与 HASH 结果分别记录。
5. 共享平台继续承担拉取前后的技术检查，最终业务验收由业务平台承担。
6. 同一版本在相同交付目标、接收方及校验要求下已下载、待通知或待验收时，后续扫描不重复下载；不同交付范围分别处理。
7. 数据执行结果与待发送通知一同持久化，恢复后可以继续补发。
8. 结果通知失败不改变已经确认的传输结果，迟到回执不回退新交付状态。
9. 失败任务不发布有效整单标记；发布结果未知先核对再判定。
10. 记录任务号、产品或文件、源版本、失败阶段和原因，让故障可以定位到责任方和具体数据。
11. FTP/SFTP 均通过已配置服务执行；协议差异由对应适配处理，不能把 FTP 命令套到 SFTP。
12. 多个监听目标独立调度并受并发限制，单次接口拉取不生成长期监听配置。
13. 页面分开显示连接、监听、任务、通知与验收状态；字节进度达到 100% 不自动关闭业务流程。
